## Vérifications

- 108 tests unitaires du service sur une base en mémoire (99 % des lignes) ; 253 tests du moteur inchangés.
- 9 tests d'intégration sur la vraie base (CI) :
  - `join_queue` écrit ticket, contact (empreinte HMAC de 32 octets), outbox, journal et messages temps réel ;
  - **deux `call_ticket` simultanés** de deux coiffeurs : un appel, un `no_eligible_ticket` ;
  - **même `command_id` envoyé deux fois en même temps** : une seule écriture, réponses identiques ;

## Choix par défaut

- **Pas de `packages/contracts` ni de zod** : le dépôt n'en a pas, et le code partagé doit tourner dans Deno sans carte d'import. La validation est écrite à la main dans `queue-service/src/request.ts`. Le TRD §4 le note ; zod pourra arriver avec les formulaires.
- **Deux `call_ticket` simultanés** : le plan (« un succès et un `invalid_transition` ») et le TRD §14 (« jamais `invalid_transition` ; le suivant ou `no_eligible_ticket` ») se contredisent. Le comportement suit le TRD, source des choix techniques : deux coiffeurs → un appel et `no_eligible_ticket` ; double appui du même coiffeur → `call_already_in_progress`. **À corriger dans le plan par Koni.**
- **Temps réel** : `realtime.send` dans la transaction, donc publié seulement si elle est validée (le TRD disait « après validation »). Le sujet `ticket-token:` est calculé en SQL ; le jeton ne remonte pas à la fonction.
- **Outbox** : une ligne `push` et une ligne `sms` par message client ; prénoms et téléphones ajoutés à l'envoi (aussi pour les push au salon) ; `params.variant` et `params.on_sent_last_notified_start_at` (K19). Documenté dans BACKEND_SCHEMA §4.16.
- **Refus enregistrés** : une commande refusée par le moteur est enregistrée dans `processed_commands` ; le rejeu renvoie le même refus. Les erreurs avant le verrou (corps invalide, accès refusé) ne sont pas enregistrées.
- **Confirmer sans fusion** un rendez-vous dont le numéro a déjà un ticket actif : `already_has_active_ticket` (code absent de la liste de `confirm_appointment`, ajouté par défaut ; sinon l'index unique ferait échouer la transaction).
- **Ticket d'un autre salon** dans une commande du personnel : le moteur répond `invalid_payload` (ticket inconnu dans le salon de l'appelant), pas `ticket_other_salon` ; les données de l'autre salon ne sont jamais chargées.
- **Membre de plusieurs salons** : le salon du ticket visé ; pour `set_presence`, celui du membre visé ; sinon `salon_id` obligatoire dans le corps.
- **Ticket de test** : prénom tiré du dictionnaire (`pro-manager.setup.test.ticket_name`) ; un second appui renvoie le test en cours.
- **`ticket-public`** : 60 appels par minute et par IP ; lien inconnu, mal formé ou expiré → même réponse `link_expired` (HTTP 410), pour qu'un code ne puisse pas être sondé.
- **`queue-tick`** : salons publiés du jour + toute journée qui a encore un ticket actif ; un passage qui ne change rien n'écrit rien (`estimate_updated_at` seul n'est pas un changement). Le prochain créneau libre est arrondi à la minute ; un créneau à l'heure courante ou passée signifie « maintenant » pour l'interface et n'est pas réécrit chaque minute.
- **Absences** : enregistrées par empreinte du numéro (`no_show_records`) ; à la 5e en 30 jours, `no_show_warning` (push et SMS), au plus une fois par 30 jours (`no_show_warnings`). Un ticket sans numéro ne compte pour personne.
- **`preview_presence_change`** : Edge Function `preview-presence-change` (BACKEND_SCHEMA le prévoyait), gérant seulement ; renvoie identifiants et codes de tickets, pas de prénoms (le tableau de bord les a déjà).
